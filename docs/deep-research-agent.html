Building a research agent that does the work

Samuel Borelli · June 2026

I was spending too much time on research. Not the reading — the find the right sources, read them, figure out what they actually mean, put it together loop. That sequence takes hours for any question with depth.

The tools exist. Search APIs, content scrapers, LLMs. But they're separate. You search, you get links, you open them, you read, you switch tabs, you synthesize. The friction of moving between tools is where the time goes. I wanted one thing that did the whole loop automatically.

What I built

A research agent built on Alibaba's ReAct loop — the model drives the research by deciding what to search for, what to read, and when it has enough. Tools execute locally. The model calls <tool_call>, code runs the tool and wraps the result in <tool_response>, the model sees it and decides the next step.

But the base loop isn't really the interesting part. What made it useful is what I built on top.

Dual-pass research

The problem with a single ReAct pass: the model can't hold two perspectives at once. If you tell it to find practitioner stories with real numbers, it will — but it won't also build a structured framework. If you guide it toward structured sourcing, you lose the messy, specific anecdotes that make research feel real.

So I built a dual-pass runner. It runs the agent twice:

  • Pass A — broad, unfiltered search. No source quality guidance. The model finds practitioner stories, named examples, specific numbers, first-hand accounts.
  • Pass B — guided search with a source quality system active. Results are classified by credibility tier. Cumulative scores track coverage. The model builds a structured framework.
  • Synthesis — the LLM merges both reports, weaving Pass A's stories into Pass B's framework as inline evidence.

The result is a report that has both real examples and a usable structure. Either pass alone would be missing something.

python src/dual_pass.py "Your research question" — the recommended way to use this.

Source quality system

The source quality system is the main custom work. Every search result is classified by a rule-based engine — domain lookups against known academic publishers (arxiv.org, pubmed, nature.com, etc.), TLD suffix checks (.gov, .mil), institutional domain matching (who.int, worldbank.org), affiliate path detection, anecdotal snippet keywords, platform host detection for Substack/Medium/Quora/Reddit, and .edu fallback logic.

Each result gets a tier label and score. A per-batch dashboard and cumulative running total are appended to every search response. The model passes the cumulative JSON blob forward through tool arguments — not a fragile memory trick, but structured state that persists across rounds because the code hands it back with every call.

The whole thing is toggled by a single environment variable. ENABLE_SOURCE_QUALITY=false runs the agent exactly like the base Alibaba code — no classification, no dashboard, no cumulative tracking.

What it produced

Today I ran it on a question about how regular people (not influencers, not course sellers) actually get jobs. The dual-pass output: 10 sourced anecdotes with real conversion rates from the first pass, a structured tactics framework from the second, and a merged report that weaves the stories into the framework.

~4 minutes per pass. ~$0.30 each. The synthesis merges both into one report. The same research manually would have been 2–3 hours and I would have stopped at 2–3 sources instead of 10.

Since then, it's produced three substantial research reports in a single session — cold email tactics, regular people's job-getting methods, and portfolio blog structure analysis. Each one covered more sources than I would have found manually.

What I'd change

The extractor prompt for page reading misses nuance in opinion-based content. It's built for extracting factual evidence, not reading between the lines of a personal story. A secondary pass focused on tone would help for qualitative research.

The cumulative scores are advisory — the model is prompted to use them but nothing enforces it. A proper programmatic gate (pause if score < 40%, or force a scholar-targeted round) would make the quality system drive behavior rather than just annotate it.

How it compares to the original

The core ReAct loop is from Alibaba-NLP/DeepResearch — 19.3k stars, Apache-2.0, a real research achievement with a custom-trained 30B MoE model. Without them, this doesn't exist.

But they built a research tool for AI researchers doing literature reviews. Their setup requires running their custom 30B model locally via vLLM — you need GPUs and patience. I built on top of their loop to make something for humans doing practical research.

Where it's different:

  • API-first. Any OpenAI-compatible provider — DeepSeek, OpenAI, OpenRouter, Claude. One env var swap. No local GPU needed.
  • Dual-pass. Two differentiated passes instead of one flat one. Practitioner stories from unfiltered search, structured framework from quality-guided search, then merged by LLM synthesis.
  • Source quality. The original treats all sources equally. Ours classifies every result into 5 tiers — peer-reviewed, scholarly, anecdotal, blog/news, affiliate — with cumulative scoring across rounds.
  • Qualitative-aware. Tier 3 (anecdotal/interview) is explicitly weighted as valuable. First-hand accounts with real numbers aren't treated as weaker than institutional sources.

It's not better in absolute terms. It's better for the specific problem I'm trying to solve: practical, qualitative research about how things actually work in the real world.

  • Loop: ReAct protocol from Alibaba-NLP/DeepResearch
  • Search: Serper.dev API + source quality classification engine
  • Reading: Jina.ai Reader API + LLM extractor (SUMMARY_MODEL_NAME configurable)
  • Scholar: Google Scholar via Serper.dev
  • Custom: source_quality.py — 417-line classification engine, dual_pass.py — 175-line dual-pass orchestrator
  • Server: MCP protocol wrapper for async dispatch
  • Model: DeepSeek V4 Flash (any OpenAI-compatible API)
  • Total: ~1,700 lines across 11 source files
